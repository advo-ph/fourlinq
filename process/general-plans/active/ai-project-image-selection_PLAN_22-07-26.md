# AI Per-Category Best-Image Selection for /inspiration

**Plan:** `ai-project-image-selection_PLAN_22-07-26.md`
**Complexity:** SIMPLE (single session; 3 artifacts, one-way data flow)
**Status:** ACTIVE

---

## Overview

The `/inspiration` page currently shows each project's `p.image` hero regardless of which filter
tab is active. This plan adds AI-powered per-category image selection: when a visitor clicks
Windows, Doors, Interior, or Exterior, every project card swaps its hero to the image that best
represents that category for that project.

The AI work happens entirely at build/author time via a one-off Node script. The frontend receives
a single generated TypeScript data file and overlays it at render time. No new runtime API calls,
no DB changes, no CMS changes.

## Locked Decisions (not renegotiated here)

| Decision | Value |
|---|---|
| AI model | `gemini-2.5-flash` via `@google/generative-ai` SDK (matches `server/lib/gemini.ts`) |
| AI method | Vision scoring (0-100 per category per image), NOT embeddings |
| Storage | Generated static TS file in `src/data/`, version-controlled |
| Schema | Hand-authored `src/data/projects.ts` stays untouched |
| Manifest key | Image path string (NOT content hash) — future enhanced-image swaps at same path keep scores |
| Category detection | AI decides which categories each image shows; hand-set `tag[]` is a fallback/override |
| Confidence threshold | 40/100 — below this a category is treated as absent for that project |
| Prompt strategy | Send ALL images of ONE project in a single Gemini call; model compares them relative to each other |

## 1. Manifest Schema

File: `server/data/project-image-analysis.json`

```
{
  "version": 1,
  "analyzedAt": "<ISO timestamp of last full run>",
  "projects": {
    "<projectId>": {
      "finished": true,
      "analyzedAt": "<ISO timestamp>",
      "images": {
        "/images/projects-fb/<name>.jpg": {
          "scores": {
            "windows":  <0-100 integer>,
            "doors":    <0-100 integer>,
            "interior": <0-100 integer>,
            "exterior": <0-100 integer>
          },
          "reasoning": "<string from Gemini, stored for debuggability, not shipped to frontend>"
        }
      }
    }
  }
}
```

TypeScript type alias (for use inside the script, not exported):

```typescript
type ImageScore = {
  scores: { windows: number; doors: number; interior: number; exterior: number };
  reasoning: string;
};
type ProjectAnalysis = {
  finished: boolean;
  analyzedAt: string;
  images: Record<string, ImageScore>;
};
type Manifest = {
  version: 1;
  analyzedAt: string;
  projects: Record<string, ProjectAnalysis>;
};
```

**Keying rule:** Keys are the canonical path strings exactly as they appear in `projects.ts`
(e.g. `/images/projects-fb/DOuJGHUl.jpg`). This means a future enhanced-image swap that keeps
the same filename keeps its existing score entry without re-analysis.

## 2. Analysis Script — Full Design

File: `server/scripts/analyze-project-images.ts`

### 2a. Imports and constants

```
import dotenv from "dotenv";
dotenv.config();                        // must be first

import { GoogleGenerativeAI, SchemaType } from "@google/generative-ai";
import fs from "fs";
import path from "path";
import { projects } from "../../src/data/projects.js";
```

Note: existing scripts in `server/scripts/` import `"../../src/data/..."` via relative path with
`.js` extension (tsx resolves `.ts` files when `.js` is referenced). Follow the same pattern.

### 2b. Named constants

```typescript
const CATEGORY_THRESHOLD = 40;          // scores below this = category absent
const MANIFEST_PATH = path.resolve("server/data/project-image-analysis.json");
const GENERATED_PATH = path.resolve("src/data/project-category-images.generated.ts");
const IMAGES_ROOT = path.resolve("public");  // images stored at public/images/projects-fb/
const BASE_DELAY_MS = 1000;             // base throttle between project API calls
const MAX_RETRIES = 5;
```

### 2c. CLI flags

Parse `process.argv`:

- `--force`: set `forceAll = true`; ignore `finished` flags; re-analyze every project.
- `--only <projectId>`: set `onlyId = <projectId>`; process exactly one project by id.

Both flags can coexist (`--force --only las-pinas-residence` re-analyzes one project from scratch).

### 2d. Manifest read / initialise

Read `MANIFEST_PATH` from disk if it exists; parse JSON into `Manifest` type. If file does not
exist, initialise an empty manifest: `{ version: 1, analyzedAt: "", projects: {} }`.

### 2e. Project enumeration

Iterate `projects` from `src/data/projects.ts`. For each project:
1. If `onlyId` is set and `project.id !== onlyId`, skip.
2. If `forceAll` is false and `manifest.projects[project.id]?.finished === true`, log
   `[SKIP] <id> (already finished)` and skip.
3. Otherwise, collect all image paths: `[project.image, ...(project.gallery ?? [])]`.

### 2f. Image byte reading

For each image path string (e.g. `/images/projects-fb/DOuJGHUl.jpg`):
- Disk path = `path.join(IMAGES_ROOT, imagePath)`.
- If file does not exist, log a warning (`[WARN] Missing on disk: <path>`) and skip that image
  (do not abort the whole project).
- Read with `fs.readFileSync(diskPath)`, convert to base64 string.
- MIME type: `"image/jpeg"` (all referenced files in projects.ts are `.jpg`).

### 2g. Gemini multimodal request — per-project single call

Use `@google/generative-ai` SDK (same package as `server/lib/gemini.ts`):

```typescript
const genAI = new GoogleGenerativeAI(process.env.GEMINI_API_KEY!);
const model = genAI.getGenerativeModel({
  model: "gemini-2.5-flash",
  generationConfig: {
    responseMimeType: "application/json",
    responseSchema: {
      type: SchemaType.OBJECT,
      properties: {
        images: {
          type: SchemaType.ARRAY,
          items: {
            type: SchemaType.OBJECT,
            properties: {
              path:      { type: SchemaType.STRING },
              scores: {
                type: SchemaType.OBJECT,
                properties: {
                  windows:  { type: SchemaType.INTEGER },
                  doors:    { type: SchemaType.INTEGER },
                  interior: { type: SchemaType.INTEGER },
                  exterior: { type: SchemaType.INTEGER },
                },
                required: ["windows", "doors", "interior", "exterior"],
              },
              reasoning: { type: SchemaType.STRING },
            },
            required: ["path", "scores", "reasoning"],
          },
        },
      },
      required: ["images"],
    },
  },
});
```

**The request parts array** is built as follows (in order):
1. A `{ text: <SYSTEM_PROMPT> }` part.
2. For each image of the project, in the same order they appear in `projects.ts`:
   a. A `{ text: "Image: <imagePath>" }` label part (so the model can echo back the path).
   b. An `{ inlineData: { mimeType: "image/jpeg", data: <base64> } }` part.

**System prompt text** (exact text to use — this is the category-definition prompt):

```
You are an expert architectural photography classifier for a premium windows and doors company (FourlinQ) in the Philippines.

You will receive a set of images from the SAME residential project. Analyse ALL of them together and score each image on how well it visually represents each of the four product categories below. Scores are 0-100 integers.

CATEGORY DEFINITIONS — be precise:
- windows: The photo's primary subject is window units — the glazing, frames, sashes, or mullion grids. Interior or exterior angle is fine as long as the WINDOW ITSELF is the hero of the composition.
- doors: The photo's primary subject is a door system — entry doors, sliding/folding glass door panels, door frames, or door hardware. French doors and accordion partitions count. Do NOT score a door in the background highly; the door must be the clear compositional focus.
- interior: The photo is taken FROM INSIDE a room and shows the interior space — flooring, ceiling, walls, furnishings, or the room volume. Windows or doors may appear, but the defining quality is the indoor point of view and interior atmosphere.
- exterior: The photo is taken from OUTSIDE and shows the building facade, street view, landscaping, or the structure's external form. An outdoor terrace or balcony looking outward also qualifies.

Notes:
- A single photo CAN score high in multiple categories (e.g. an interior shot centered on a door scores high in both "interior" and "doors").
- A score of 0 means the category is completely absent from the image.
- A score of 100 means the image is a textbook example of that category.
- For each image, echo back EXACTLY the path label you were given (e.g. "/images/projects-fb/DOuJGHUl.jpg") as the "path" field.
- In the "reasoning" field, write 1-2 sentences explaining why you gave those scores. Be specific about what you see.
- Compare the images relative to each other: if multiple images all show windows, the one that makes windows the most prominent subject should score highest.

Return a JSON object matching this schema: { "images": [ { "path": string, "scores": { "windows": int, "doors": int, "interior": int, "exterior": int }, "reasoning": string }, ... ] }
```

Call: `const result = await model.generateContent({ contents: [{ role: "user", parts }] });`

Parse response: `JSON.parse(result.response.text())` → validate it has `images` array.

### 2h. Retry / rate-limit handling

Wrap the `model.generateContent(...)` call in an exponential-backoff loop identical to the
pattern in `server/scripts/seed-embeddings.ts`:
- Up to `MAX_RETRIES` attempts.
- Detect transient errors: `/429|503|rate|quota|timeout|fetch failed/i`.
- Delay: `Math.min(BASE_DELAY_MS * Math.pow(2, attempt), 30_000)` ms.
- Non-transient errors: break immediately and log; mark project as NOT finished.

Between project calls, always `await sleep(BASE_DELAY_MS)` to avoid burst rate limiting.

### 2i. Manifest update — per project

After a successful API response for a project:
1. For each image entry in the response `images` array, store into
   `manifest.projects[project.id].images[entry.path]` the `{ scores, reasoning }` object.
   - If a path the model returned does not match any known image path for that project, log a
     warning and skip (model hallucination guard).
2. Set `manifest.projects[project.id].finished = true`.
3. Set `manifest.projects[project.id].analyzedAt = new Date().toISOString()`.
4. **Write the manifest to disk immediately after each project** (not only at the end). This ensures
   partial progress is preserved if the script is interrupted mid-run.

### 2j. Best-per-category selection and threshold logic

After all projects are processed (or after re-loading the now-updated manifest), iterate
`manifest.projects`. For each project:

For each category `c` in `["windows", "doors", "interior", "exterior"]`:
1. Collect all images for this project that have a score entry.
2. Find the image with the highest `scores[c]`.
3. If that score is `< CATEGORY_THRESHOLD` (40), the category is considered absent — do not
   assign a best image for it, and do not include this category in derived tags.
4. Otherwise, record `bestImages[project.id][c] = imagePath`.

Derive tags: `derivedTags[project.id]` = the set of categories that passed the threshold.

### 2k. Generated frontend file output

Write `src/data/project-category-images.generated.ts` with:

```typescript
// AUTO-GENERATED by server/scripts/analyze-project-images.ts — do not edit.
// Re-run with: npm run analyze:projects
// Last generated: <ISO timestamp>

import type { InspirationTag } from "./projects";

export const projectCategoryImages: Record<
  string,
  Partial<Record<InspirationTag, string>>
> = {
  "<projectId>": {
    windows:  "<imagePath | omitted if below threshold>",
    doors:    "<imagePath | omitted if below threshold>",
    interior: "<imagePath | omitted if below threshold>",
    exterior: "<imagePath | omitted if below threshold>",
  },
  // ... one entry per project
};

export const projectDerivedTags: Record<string, InspirationTag[]> = {
  "<projectId>": ["windows", "doors"],   // only categories that passed threshold
  // ...
};
```

All four category keys are only included when they pass the threshold. A project with no passing
categories gets an empty object `{}` and an empty array `[]`.

The file is formatted as a TypeScript object literal (not JSON) so it type-checks with the rest
of the codebase and ships with the Vite build without any loader config changes.

After writing the generated file, print a human-readable console table:

Columns: project id | per-category: `<filename> (score)` or `-` if absent/below threshold.

Also write the same report to `server/data/project-image-analysis-report.md` as a Markdown table

### 2m. Main function skeleton

```typescript
async function main() {
  const forceAll = process.argv.includes("--force");
  const onlyIdx = process.argv.indexOf("--only");
  const onlyId = onlyIdx >= 0 ? process.argv[onlyIdx + 1] : null;

  const manifest = loadManifest();
  const toProcess = projects.filter(p => {
    if (onlyId && p.id !== onlyId) return false;
    if (!forceAll && manifest.projects[p.id]?.finished) return false;
    return true;
  });

  console.log(`[analyze] ${toProcess.length} project(s) to process`);

  for (const project of toProcess) {
    await analyzeProject(project, manifest, forceAll);
    await sleep(BASE_DELAY_MS);
  }

  manifest.analyzedAt = new Date().toISOString();
  writeManifest(manifest);

  const { bestImages, derivedTags } = selectBest(manifest);
  writeGeneratedFile(bestImages, derivedTags);
  printReport(bestImages, manifest);
}

main().catch(e => { console.error(e); process.exit(1); });
```

### 4c. Tag derivation overlay in `toView` — OPTIONAL enhancement

Currently `toView` uses `p.tag?.length ? p.tag : tagFromCategory(p.category)`. We can optionally
also fall through to `projectDerivedTags[p.id]` when both `p.tag` is empty AND `tagFromCategory`
returns `[]`. Decision: keep this as a SECONDARY fallback to avoid breaking the carefully
hand-authored `tag[]` values in projects.ts. The exact expression is:

```typescript
tag: p.tag?.length
  ? p.tag
  : (tagFromCategory(p.category).length
      ? tagFromCategory(p.category)
      : (projectDerivedTags[p.id] ?? [])),
```

This means: hand-set tags win; legacy category-derived tags win; AI-derived tags are the final
fallback. This is safe because all 12 current projects already have `tag[]` set.

at line 98-104. Change the `src` attribute from:


to:

```tsx
src={
```

## 8. Rollout / Incremental Workflow (How to Add a New Project or Swap an Enhanced Image Later)

### Adding a new project

1. Add the project entry to `src/data/projects.ts` with a new `id`, `image`, optional `gallery`,
   and `tag[]`.
2. Copy the new image files to `public/images/projects-fb/`.
3. Run: `npm run analyze:projects` (incremental — only new projects are processed).
4. Inspect the report for the new project's row.
5. Commit `server/data/project-image-analysis.json` and the regenerated
   `src/data/project-category-images.generated.ts`.
6. Deploy (push to main → auto-deploy).

### Swapping an enhanced image (same filename, higher quality)

Because the manifest is keyed by image **path** (not content hash), swapping a `.jpg` on disk at
the same path does NOT invalidate the existing score. The existing scores remain in the manifest
and the generated TS is unchanged. The new image will appear on the frontend after deploy.

If you want the AI to re-evaluate the enhanced image (e.g., you believe the new version would
score differently):
```bash
npm run analyze:projects -- --force --only <projectId>
```

Then commit the updated manifest + regenerated TS.

### Swapping an enhanced image (new filename)

If the new image has a different filename (new path), the old path entry in the manifest becomes
stale. The new path will be missing from the manifest, so the script will pick it up as
un-analyzed on the next incremental run:
```bash
npm run analyze:projects -- --only <projectId>
```

Note: `finished` will still be true for the project from the old run. This means the incremental
run will skip it. Use `--force --only <projectId>` to force a fresh analysis of the updated image
set.

## 9. Risks and Mitigations

### API cost estimate

- 12 projects × 1 call per project = **12 Gemini API calls total**.
- Each call contains 1-5 images (42 images total across 12 projects, average ~3.5).
- `gemini-2.5-flash` multimodal pricing is very low for this scale. Estimated cost < $0.10
  for the full initial run. Negligible.
- Re-runs are also cheap: `--only` limits to 1 project (1 call).

### Rate limiting

- The exponential backoff loop handles 429/503 responses (same pattern as `seed-embeddings.ts`).
- The `BASE_DELAY_MS` throttle between projects prevents burst. With 12 projects and 1s delay
  the full run completes in ~30-60 seconds.

### Score non-determinism between runs

- AI models can produce slightly different scores on repeated calls for the same images.
- The manifest persists scores from the first (or last `--force`) run. Incremental runs do not
  re-analyze `finished` projects, so production scores are stable once committed.
- This means scores are "locked" per run, which is the desired behaviour.

### A project is tagged but no image passes threshold

- Scenario: `projects.ts` has `tag: ["exterior"]` but no image scores >= 40 for `exterior`.
- The generated file will have no `exterior` key for that project.
- The `derivedTags` for that project will not include `exterior`.
- In Inspiration.tsx, `projectCategoryImages[p.id]?.exterior` is `undefined`, so the fallback
  `?? p.image` shows the hero — acceptable graceful degradation.
- Filtering: the project's `tag` in `projects.ts` already contains `exterior`, so the project
  still appears in the exterior filter tab (the hand-set tag wins over derived tags). It just
  shows the hero image instead of a best-category pick.
- This is a reasonable UX outcome: the project appears, but the image is the generic hero.

### Images physically absent on disk

- If a file referenced in `projects.ts` is missing from `public/images/projects-fb/`, the script
  logs `[WARN] Missing on disk: <path>` and skips that image.
- The API call proceeds with the images that ARE present.
- If the hero image is the one missing, the project card will show a broken `<img>` on the
  frontend — but this is already broken before this feature, not caused by it.
- After deployment, broken image paths should be investigated separately.

### TypeScript compilation of the generated file

- The generated file uses `Partial<Record<InspirationTag, string>>` which is safe even if no
  categories pass threshold (produces `{}`).
- The import path `@/data/project-category-images.generated` must resolve via Vite's `@/`
  alias → `src/`. Verify `vite.config.ts` has `resolve.alias["@"] = path.resolve("src")` (it
  should, as all other `@/data/` imports work).
- The `.generated.ts` file must be committed before running `npm run typecheck` or `npm run
  build`, since Inspiration.tsx imports it. If the file is absent, the build fails with a
  module-not-found error. The checklist step ordering ensures the script runs (creating the file)
  before typecheck runs.

### Gemini response schema violations

- If `responseMimeType: "application/json"` + `responseSchema` is set, Gemini is constrained to
  emit valid JSON matching the schema. The risk of malformed JSON is very low.
- The script should still wrap the `JSON.parse` in a try/catch; on parse failure, log the raw
  response and mark the project as NOT finished (so the next incremental run retries it).
- If the model returns a `path` that does not match any image in the project, the hallucination
  guard (step 2i) logs a warning and skips the rogue entry.
